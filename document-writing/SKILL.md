# 文档与演示文稿写作

将用户的材料写成能由其指定作者署名、由目标读者直接阅读的成稿。文档应完成自身的沟通任务，而不是说明助手如何制作这份文档。

本技能约束内容与表达，不规定统一文体、章节结构、文件格式或排版。用户要求、文档用途和既有模板决定具体形式。

## 适用范围

仅在用户请求起草、编写、润色、改写或审阅文档、演示文稿等成稿文字时使用。适用对象包括文档正文、摘要、图表说明、附件说明，以及PPT提纲、页标题、页内文案和讲稿。

普通聊天、概念问答、临时解释、代码与代码注释编写不使用本技能。纯视觉设计、排版、文件转换或程序运行也不触发；此类任务同时包含成稿文字修改时，只对该部分应用写作规则。

文档与PPT的格式、模板、视觉布局和文件生成遵循各自要求。本技能负责文字的立场、内容与表达，不接管这些制作流程。

## 一、先建立写作定位

起草前，根据用户要求及已有材料确定以下事项；能够推断时直接采用合理判断，不必逐项询问：

- **作者角色**：个人、项目组、组织、研究者、产品方或其他指定主体。
- **目标读者**：读者已经知道什么，需要理解、判断或执行什么。
- **文档任务**：例如解释结果、提出方案、记录事实、指导操作、申请支持或表达个人立场。
- **文体约束**：正式程度、人称习惯、证据要求、篇幅、模板及必需内容。

据此确定叙述立场和内容取舍。作者立场不等于必须使用第一人称，也不意味着全文必须去除第一人称。

若任务与模板存在差异，遵从用户对本次成稿的要求；模板中的示例事实、身份和经历不能直接当作作者的真实情况。

## 二、区分三类常见问题

### 1. 作者角色错位

成稿站在助手、编辑或交付者的角度，向作者解释“这份文档可以怎样使用”，而没有直接面向文档读者。

修正方法：把句子放回文档的真实交流关系中。明确该段应陈述的事实、方法、判断或行动，而不是机械地把“你”替换成“我”。

### 2. 人称机械化

将“以用户为作者”误解为给每个动作加上“我”；或者反向过度修正，把所有“我”换成“本设计”“本文”。两种做法都会使主语重复、语气生硬。

修正方法：先判断是否需要显式主语，再选择自然且准确的主体。作者身份通过内容责任和论述立场体现，不通过代词出现次数体现。

### 3. 制作过程侵入正文

将生成、导出、保存、排版、交付或使用建议写进正文，而这些内容没有服务该文档本身的目的。例如，在研究报告中写“图片可用于报告与展示”。

修正方法：检查这项信息对读者的实际作用。必要的方法、数据处理和操作流程留在正文；仅用于帮助用户接收或继续编辑文件的信息，放在交付消息中，通常无需写入文档。

## 三、按文体选择人称和主语

不要统一替换全文的人称。按语境处理：

| 文档或语境 | 优先表达方式 | 判断依据 |
| --- | --- | --- |
| 研究、技术、分析报告 | 直接陈述方法与结果；必要时用“本研究”“本设计”“本实验” | 强调对象、方法和证据，减少叙事者干扰 |
| 方案、建议书 | 用“本方案”“项目组”“实施团队”等明确主体 | 提议、承诺与责任需要能够归属 |
| PPT、演示文稿及讲稿 | 页标题明确本页主题或判断，正文呈现支撑信息；讲稿按讲述者角色自然表达 | 页内文字便于快速阅读，讲稿承担解释与衔接，不机械复制长篇报告段落 |
| 操作手册、流程规范 | 使用清楚的动作指令或角色名称 | 让执行者知道谁在何时做什么 |
| 工作总结、述职、个人陈述 | 按机构习惯使用第一人称、岗位名称或省略主语 | 需要呈现个人职责、贡献或经历 |
| 书信、申请、致辞、反思文字 | 根据关系和语气自然使用“我”“我们” | 个人态度与关系本身就是内容 |

具体处理时：

- 上下文已明确动作主体时，直接写动作即可。例如“将样本划分为训练集和测试集”。
- 需要区分方案、实验或实现时，使用准确主体。例如“本实验采用分层抽样”“在代码实现中设置速度上限”。
- 涉及责任、承诺或多方协作时，写明实际主体；不要为了“客观”而把责任隐藏在被动句中。
- 第一人称承担真实的个人经验、判断、承诺或反思时保留，不把它当作错误词删除。
- “本设计”“本文”等称谓必须与文档对象一致，避免在工作总结中凭空出现“本实验”。

## 四、按内容作用区分正文与交付说明

对“文件、代码、图像、附件、格式、保存、导出、可用于”等表述做语义检查，不将这些词直接列为禁词。

逐句判断：

1. 该信息是否回答了目标读者关于问题、方法、结果、责任或操作的需要？
2. 若不写，是否会影响理解、判断、执行或复现？
3. 它描述的是业务或研究过程，还是这份文档被制作、交付和后续编辑的过程？

处理原则：

- **属于正文**：算法模块如何协作、统计口径如何定义、材料如何处理、操作手册要求把结果保存到哪里、附件提供何种证据等。
- **通常属于交付消息**：已生成多少张图片、文件可以插入报告、哪里需要用户填姓名、用哪个软件打开、需要如何更新目录等。
- **取决于文档任务**：导出格式、存储位置、执行命令和文件清单。复现附录、接口文档或操作手册可能需要这些内容；分析结论通常不需要。

不要把“可用于……”一律删除，应判断用途是否对读者有意义。“该指标用于比较收敛速度”说明方法；“该图可用于撰写本报告”描述制作环节。

“本报告分析了……”可以合法交代范围。问题在于无效的自我指涉，而不是是否出现“报告”二字。

## 五、写出完成态内容

- 方法段说明采用了什么方法、关键参数和设计依据；结果段陈述观察及其含义；方案段说明拟采取的行动及理由。区分已完成、计划中和建议事项。
- 用事实、动作和证据推进段落，避免“这里可以写……”“建议补充一张图……”等编辑提示进入成稿。用户明确要求提纲、模板或批注时例外。
- 保留实际的来源边界。不能为了让文字像作者亲历而编造经历、实验、独立完成情况或贡献。
- 图表说明解释比较关系、变化趋势和关键数值；与正文关联，而不只说“该图能展示效果”。没有足够数据支持时，不编造趋势。
- 附件与复现章节说明相关实现、记录及验证方法；不要写成助手向用户交代文件包用途的清单。
- 限定条件应具体且与结论有关，按第六节判断其必要性与放置位置。
- 不为显得专业堆砌“本文”“本项目”或被动句。允许相邻句省略重复主语，也允许直接写“结果表明”“代码采用”。

## 六、避免防御性写作

防御性写作是指表达围绕预想的质疑反复自我保护，使有依据的主张被免责、让步和犹豫词遮住。判断依据是句子的作用，而非某个词是否出现。

写作与改稿时执行以下规则：

1. **优先陈述实际内容**：直接交代对象、行动、方法、发现或建议，随后给出依据。不要用一串“并非试图”“并不声称”代替对实际工作的说明。章节安排仍服从文体和论证需要。
2. **用正向范围界定主张**：将已知的对象、样本、条件或时间范围写进判断。例如，将泛泛的“不能推广到所有情况”改为原材料明确支持的适用范围，不新增范围信息。
3. **删除没有新增信息的自辩**：去掉无依据的自我贬低、预设批评、反复声明没有表达某种意思，以及段末惯例式的“当然仍有局限”。真实的更正、责任说明或异议回应按其作用保留。
4. **校准不确定性**：证据支持明确陈述时直接陈述；真实不确定性使用准确限定，并在材料支持时说明来源及影响。不要把“可能、或许、一定程度上”层层叠加，也不要把它们一律删除。
5. **让限制各有位置**：样本与方法条件写在相关方法或主张处；集中讨论的限制可放入相应章节。会实质改变当前判断、操作或风险的条件，应在读者作出判断前明确，不能藏到附录。已经说明的同一限制不在每个结果后重复。
6. **让对比服务论证**：“不是A而是B”“虽然……但是……”应有实际辨析对象和论证作用。没有需要澄清的歧义时，直接说清B，不主动引入无关反例和假想误读。
7. **锁定主张强度**：精简语言后，数值、对象、条件、证据强弱、完成状态与承诺范围应保持一致。相关关系不能改成因果关系，局部观察不能扩为普遍规律，有限改善不能改成全面优越。

处理顺序为**诊断—必要性审阅—定点改写—事实复核**。先区分冗余辩解、必要范围、真实不确定性和有效概念区分，再决定删除、合并、正向重述或原样保留，不先把全文改得“更自信”。

- 用户要求只诊断时，列出位置、原句、问题、判断依据和修改方向，不直接改正文。
- 用户已要求修改时，在编辑过程中完成诊断和审阅，再修改相关句段；不额外要求用户逐条确认。只有缺失信息影响事实判断或承诺时才澄清。
- 原文没有给出发现或结论时，只能整理已知的目的、方法或对象；不能为了“主张先说”编造发现。

处理长文或防御性表达较密集的段落时，阅读 [反防御性写作诊断与改写示例](references/anti-defensive-writing.md)。其中包含不同文体的处理方法，以及基于用户提供帖子整理的设计依据。

## 七、改写示例

以下例子说明判断方法，不要求套用固定句式。

| 场景 | 问题表述 | 合适的改写 |
| --- | --- | --- |
| 方法说明 | 我将数据集划分为两个部分。 | 将数据集划分为两个部分。材料提供了划分依据、用途或比例时，再补充相应内容。 |
| 算法实现 | 我在代码中设置了最大迭代次数。 | 在代码实现中设置最大迭代次数，作为搜索过程的终止上限。 |
| 实验报告 | 图像保存为PNG，可以用于报告与展示。 | 若格式无关，删除该句；根据实际数据改写为该图所支持的观察或结论。 |
| 方法章节 | 这个表格方便你对比两个算法。 | 两种算法采用相同的评价预算，参数配置见表2-1。 |
| 项目方案 | 我们会把这些文件发给你，方便后续使用。 | 根据实际交付约定写明交付物、接收方和验收方式；若该段只是成稿交付提示，则移出正文。 |
| 操作手册 | 图片保存到指定目录，可用于后续处理。 | 处理完成后，将图像保存至约定目录，并按任务编号命名。目录与命名要求必须来自已知流程。 |
| 责任分工 | 将在下周完成审批。 | 财务负责人于下周完成审批。负责人和期限须有材料依据。 |
| 个人申请 | 我希望申请该岗位，因为…… | 若表达个人动机，保留“我”，按真实经历展开理由。 |

示例中的分类、目的、角色与期限都不是可直接套用的事实。改写时不得为了补齐句式新增未经提供的信息。

## 八、成稿审阅

完成初稿后，按意义通读，而不是只搜索代词：

1. **角色检查**：这句话是否像指定作者面向真实读者说的话？是否出现助手在向作者解释交付物的口吻？
2. **主语检查**：显式主语是否有区分主体、承担责任或表达态度的作用？省略后更清楚就省略，不批量替换成“本设计”。
3. **内容检查**：每段是否完成该章节的任务？是否残留制作提示、使用建议、文件交付话术或自指循环？
4. **证据检查**：行为主体、完成状态、数值、经历和结论是否有依据？是否因改写而扩大承诺或改变事实？
5. **连贯检查**：先解释现象或设计，再给出依据和含义；删去重复套话，保留必要的衔接。
6. **防御性表达检查**：每处限定是否增加必要信息？同一限制是否重复？是否用假想反驳遮住主张？删改后是否不当地增强了确定性、因果性或适用范围？

修订已有文档时，同时检查摘要、正文、图表说明、表内文字、结论与附件，不只处理用户指出的那一处。保持用户已确认的事实与文体选择；不要把模板说明或引用中的人称当作作者正文批量改写。

审阅通过标准：成稿可由指定作者直接署名并交给目标读者阅读；正文不依赖读者了解文档由谁代写、生成或交付，且表达方式符合该文档的沟通目的。
